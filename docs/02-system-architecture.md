## 1. Overview — সিস্টেমটা কীভাবে কাজ করবে?

### 1.1 এক লাইনে

**Admin প্রশ্ন জোগাড় করে → AI যাচাই করে Knowledge Base বানায় → Student সেই Knowledge Base থেকে শেখে ও পরীক্ষা দেয়।**

Student কখনো সরাসরি ইন্টারনেট থেকে প্রশ্ন পায় না। Live internet থেকে প্রশ্ন তোলা MVP-তে হবে না — যাচাই করা Knowledge Base-ই হবে সত্যের একমাত্র উৎস (PRD 1.3)।

### 1.2 ডিজাইনের মূল নীতি

1. **Knowledge Base-ই সত্যের উৎস** — AI শেখানো, প্রশ্ন বানানো, ব্যাখ্যা দেওয়া — সবকিছুর ভিত্তি KB। KB-তে নেই এমন তথ্য AI বানিয়ে বলবে না।
2. **Admin রিভিউ গেট** — AI যা-ই তৈরি করুক (প্রশ্ন, ব্যাখ্যা, টপিক ট্যাগ), সন্দেহ থাকলে সেটা Student-এর কাছে যাওয়ার আগে Admin রিভিউ-তে আটকে যাবে।
3. **MVP ছোট রাখা** — একটাই ক্যাটাগরি (পেট্রোবাংলা), দুটো ড্যাশবোর্ড (Admin + Student), Web প্রথমে। BCS / Bank / অন্য ক্যাটাগরি, Voice Input, Handwritten OCR, Payment — এগুলো Phase 2-এ, এই আর্কিটেকচারে তাদের জন্য জায়গা রাখা থাকবে, কিন্তু MVP-তে বানানো হবে না।
4. **পরিচিত স্ট্যাক** — Toufiql-এর আগের কাজের সঙ্গে মিলিয়ে স্ট্যাক বাছা হয়েছে (নিচে 3 নম্বর সেকশন), যাতে নতুন কিছু শিখতে না হয়।
5. **খরচ নিয়ন্ত্রণ** — LLM কল সবচেয়ে খরচের জায়গা। তাই একই প্রশ্ন / একই ব্যাখ্যা বারবার LLM-কে জিজ্ঞেস করা হবে না — একবার বানিয়ে KB-তে জমিয়ে রাখা হবে।

## 3. Technology Stack (প্রস্তাবিত)

> "প্রস্তাবিত" মানে: এই স্ট্যাক দিয়েই শুরু করার পরামর্শ, কিন্তু চূড়ান্ত সিদ্ধান্ত ডেভেলপমেন্ট শুরুর আগে নিতে হবে। 12 নম্বর সেকশনে খোলা সিদ্ধান্তগুলোর তালিকা আছে।

| স্তর | প্রস্তাবিত প্রযুক্তি | কেন |
| --- | --- | --- |
| Frontend | **Next.js 16 + React + TypeScript + Tailwind CSS** | Nex Matrix System পোর্টফোলিওতেও একই স্ট্যাক — পরিচিত, Web-এ ভালো, মোবাইল রেসপন্সিভ করা সহজ |
| Backend | **Node.js + Express + TypeScript** | ParcelMe ব্যাকএন্ডেও Express — একই ধরনের API, Auth, RBAC প্যাটার্ন ব্যবহার করা যাবে |
| ORM + Database | **Prisma + MySQL (utf8mb4)** | বাংলা টেক্সটের জন্য utf8mb4 দরকার; Prisma দিয়ে স্কিমা এক জায়গায় থাকবে (ডক 03-এ বিস্তারিত) |
| Auth | **JWT (Access + Refresh)** + রোল-ভিত্তিক অ্যাক্সেস (Student / Admin) | PRD-তে লগইন পদ্ধতি (Email / Phone) এখনো চূড়ান্ত হয়নি — Auth ডিজাইন এমন হবে যাতে Email বা Phone, যেটাই ঠিক হোক, বসানো যায় |
| AI / LLM | **বাইরের LLM API** (প্রোভাইডার এখনো ঠিক হয়নি) — Backend-এর একটি আলাদা মডিউল থেকে কল হবে | মডেল বদলাতে হলে শুধু এই মডিউলটা বদলাবে, বাকি সিস্টেম ছোঁয়া লাগবে না |
| Job Queue | **সহজ কিউ** — শুরুতে ডেটাবেস-ভিত্তিক জব টেবিল; পরে প্রয়োজনে Redis / BullMQ | Scrape ও Upload প্রসেসিং ব্যাকগ্রাউন্ডে চালাতে হবে; MVP-তে ভারী কিউ সিস্টেম দরকার নেই |
| File Storage | শুরুতে সার্ভার / অবজেক্ট স্টোরেজ (যেমন S3-ধরনের); লোকাল ডিস্ক নয় | আপলোড করা PDF / ছবি পরে অন্য সার্ভারেও চলতে হবে |
| Hosting | এখনো ঠিক হয়নি — Frontend Vercel-ধরনের, Backend + MySQL আলাদা হোস্টিং (ডক 05-এ সিদ্ধান্ত) | MVP-তে খরচ কম রাখতে হবে; হোস্টিং সিদ্ধান্ত ডেভেলপমেন্ট শুরুর আগে নিতে হবে |

## 4. Ingestion Pipeline — প্রশ্ন কীভাবে Knowledge Base-এ যায়?

এটাই Examine-এর সবচেয়ে গুরুত্বপূর্ণ প্রবাহ। Admin Scrape বলুক বা ফাইল আপলোড করুক — দুটো রাস্তাই একই পাইপলাইনে এসে মিলবে।

```
Admin: Scrape বলল / ফাইল আপলোড করল
        │
        ▼
[1] Job তৈরি (Queue-তে) — Admin সঙ্গে সঙ্গে রেসপন্স পায়,
    প্রসেসিং ব্যাকগ্রাউন্ডে চলে
        │
        ▼
[2] সংগ্রহ (Collect)
    • Scrape: সোর্স সাইট থেকে প্রশ্ন তোলা (শুধু নতুন বছর — নিচে 4.1)
    • Upload: PDF / ছবি থেকে টেক্সট বের করা (প্রিন্ট করা প্রশ্নের OCR)
        │
        ▼
[3] ভাঙা (Parse) — প্রশ্ন, অপশন, সঠিক উত্তর, বছর, সাবজেক্ট আলাদা করা
        │
        ▼
[4] Duplicate Detection — KB-তে হুবহু / প্রায় একই প্রশ্ন আছে কিনা
        │   (ডুপ্লিকেট হলে বাদ — কিন্তু "কতবার এসেছে" কাউন্ট বাড়বে)
        ▼
[5] Topic + Pattern Analysis — টপিক ট্যাগ, প্যাটার্ন চেনা
        │
        ▼
[6] Occurrence Detection — এই প্রশ্ন / টপিক কতবার এসেছে, গোনা
        │
        ▼
[7] Confidence Check — AI নিজে নিশ্চিত কিনা?
    • নিশ্চিত হলে → সরাসরি KB-তে
    • সন্দেহ থাকলে → Admin Review Queue-তে (Student দেখবে না)
        │
        ▼
[8] Knowledge Base Update + Year Tracking
    • প্রশ্ন, টপিক, বছর, সোর্সসহ জমা
    • কোন বছরের প্রশ্ন KB-তে আছে, তার তালিকা আপডেট
```

### 4.1 Year Tracking — কীভাবে কাজ করবে?

- প্রতিটি ক্যাটাগরির জন্য KB-তে একটি তালিকা থাকবে: কোন কোন বছরের প্রশ্ন ইতিমধ্যে আছে (যেমন: PetroBangla IT — 2019, 2021, 2023)।
- Admin আবার Scrape করতে বললে সিস্টেম প্রথমে এই তালিকা দেখবে, তারপর শুধু সেই বছরগুলো খুঁজবে যেগুলো তালিকায় নেই।
- ফলে দ্বিতীয়বার স্ক্র্যাপে আগের বছরের প্রশ্ন আবার তোলা হবে না — সময় কমবে, ডুপ্লিকেট কমবে, Efficiency বাড়বে (PRD 3.5)।
- Manual Upload-এও একই নিয়ম: আপলোড করা প্রশ্নপত্রের বছর KB-তে থাকলে সিস্টেম Admin-কে জানাবে, তবুও Admin চাইলে রিভিউ করে রাখতে পারবে (যেমন: একই বছরের আলাদা সেট)।

### 4.2 Duplicate Detection — কীভাবে বুঝবে একই প্রশ্ন?

দুই স্তরে:

1. **হুবহু মিল (Exact)** — প্রশ্নের টেক্সট পরিষ্কার করে (স্পেস, বিরামচিহ্ন ঠিক করে) হুবহু মিললে ডুপ্লিকেট।
2. **প্রায় একই (Near-duplicate)** — সংখ্যা বা নাম বদলে একই প্রশ্ন (যেমন: "৫%-এর মান কত?" বনাম "১০%-এর মান কত?") — AI / টেক্সট সাদৃশ্য দিয়ে ধরা হবে। সন্দেহ থাকলে Admin Review-তে যাবে, নিজে থেকে বাদ দেওয়া হবে না।

ডুপ্লিকেট পাওয়া গেলে প্রশ্নটি আবার KB-তে ঢুকবে না, কিন্তু তার **Occurrence Count বাড়বে** — কারণ "এই প্রশ্ন কতবার এসেছে" জানাটাই Occurrence Detection-এর কাজ।

### 4.3 Scrape-এর সীমা (আগে থেকে জেনে রাখা ভালো)

- ইন্টারনেটের প্রশ্ন সব জায়গায় এক ফরম্যাটে থাকে না; অনেক সাইটে ভুল উত্তরও থাকে। তাই Scrape-কে কখনোই "সরাসরি Student-কে দেখানো" যাবে না — সবসময় এই পাইপলাইন পেরিয়ে, যাচাই হয়ে KB-তে যেতে হবে।
- কোনো সাইট স্ক্র্যাপ করতে না দিলে (robots.txt / ব্লক) সেই সোর্স বাদ দিয়ে Manual Upload-ই ভরসা। সোর্সের তালিকা ও অনুমতির বিষয়টি ডেভেলপমেন্টের আগে ঠিক করতে হবে (12 নম্বর সেকশন)।

## 5. Knowledge Base — কীভাবে সাজানো থাকবে?

### 5.1 KB-তে প্রতিটি প্রশ্নের সঙ্গে যা থাকবে

- প্রশ্নের টেক্সট, অপশন (MCQ হলে), সঠিক উত্তর
- ক্যাটাগরি (MVP-তে শুধু PetroBangla), সাবজেক্ট, টপিক, সাব-টপিক
- বছর, সোর্স (কোথা থেকে নেওয়া)
- Occurrence Count — কতবার এসেছে
- Difficulty — Easy / Medium / Hard (শুরুতে AI অনুমান, পরে Student-দের ফল থেকে ঠিক হবে)
- Status — Verified / Pending Review

সম্পূর্ণ টেবিলের নকশা `03-database-schema.md`-এ থাকবে।

### 5.2 KB কীভাবে ব্যবহার হবে?

| ব্যবহার | কীভাবে |
| --- | --- |
| Student শেখা | টপিক বেছে নিলে AI KB থেকে ওই টপিকের ব্যাখ্যা, আগের প্রশ্নের উদাহরণ, কতবার এসেছে — সাজিয়ে দেবে |
| প্রশ্ন বানানো | AI KB-র প্রশ্নের **প্যাটার্ন** দেখে নতুন প্রশ্ন বানাবে — হুবহু কপি নয় |
| ব্যাখ্যা দেওয়া | ব্যাখ্যা শুধু KB-র যাচাই করা তথ্যের ওপর ভিত্তি করে হবে |

### 5.3 Vector Database কি লাগবে?

**MVP-তে না।** PetroBangla — একটাই ক্যাটাগরি, সাবজেক্ট ও টপিকের সংখ্যা সীমিত। টপিক-ট্যাগ ও বছর দিয়ে খুঁজলেই KB থেকে সঠিক প্রশ্ন পাওয়া যাবে। Vector Search (Embedding) পরে যোগ করা যাবে, যখন ক্যাটাগরি বাড়বে বা প্রশ্নের সংখ্যা অনেক বড় হবে। আর্কিটেকচারে সেই জায়গা খোলা থাকবে, কিন্তু MVP-তে এর খরচ ও জটিলতা নেওয়া হবে না।

## 6. AI Learning System — AI কীভাবে পড়াবে?

### 6.1 প্রবাহ

```
Student টপিক বেছে নিল
        │
        ▼
Backend KB থেকে ওই টপিকের প্রশ্ন + Occurrence + বছর টেনে আনে
        │
        ▼
LLM-কে দেওয়া হয়: টপিক + KB-র তথ্য + Student-এর Skill Level
        │
        ▼
LLM বানায়: সারাংশ → আগের প্রশ্নের ধারা → উদাহরণ + ব্যাখ্যা
        → সম্পর্কিত পড়া → (সম্ভব হলে) গ্রাফ / ডায়াগ্রাম
        │
        ▼
Student-কে দেখানো হয় (বাংলায়, উদাহরণসহ)
```

### 6.2 Grounding নিয়ম (সবচেয়ে জরুরি)

- LLM-কে শুধু KB-র তথ্য দিয়ে উত্তর বানাতে বলা হবে — নিজের মনে করে তথ্য যোগ করতে পারবে না।
- KB-তে নেই এমন কিছু জানতে চাইলে AI "জানি না / KB-তে নেই" বলবে, বানিয়ে বলবে না।
- প্রতিটি ব্যাখ্যার সঙ্গে সম্ভব হলে আগের প্রশ্নের রেফারেন্স (বছর) থাকবে।

### 6.3 গ্রাফ / অ্যানিমেশন

- যেখানে বোঝাতে সাহায্য করবে, সেখানে ব্যবহার হবে — সাজানোর জন্য নয় (PRD 5.2)।
- যেমন: Math-এ গ্রাফ, প্রক্রিয়া বোঝাতে ধাপের ডায়াগ্রাম, তুলনা টেবিল।
- Frontend-এ এগুলো সাধারণ চার্ট / SVG দিয়ে বানানো হবে; ভারী ভিডিও অ্যানিমেশন MVP-তে নয়।

## 7. Adaptive Exam System — পরীক্ষা ও Skill Engine

### 7.1 Skill Model

- প্রতিটি Student-এর প্রতিটি **সাবজেক্টে** আলাদা Skill Level থাকবে (Beginner / Intermediate / Advanced)।
- প্রতিটি **টপিকেও** আলাদা স্কোর থাকবে।
- সবাই শুরু করবে **Beginner / Noob** হিসেবে।

### 7.2 প্রশ্ন বাছাই ও বানানো

```
Student পরীক্ষা শুরু করল (সাবজেক্ট + টপিক)
        │
        ▼
Backend তার Skill Level দেখল
        │
        ▼
AI KB-র প্যাটার্ন দেখে ওই লেভেলের প্রশ্ন বানাল
    • Beginner → সহজ প্রশ্ন বেশি
    • ভালো করছে → ধীরে ধীরে কঠিন প্রশ্ন
        │
        ▼
প্রশ্নের উত্তর AI নিজে যাচাই করল
    • ঠিক থাকলে → পরীক্ষায় দেওয়া হলো
    • সন্দেহ থাকলে → Admin Review Queue-তে, Student পেল না
        │
        ▼
পরীক্ষা শেষে AI খাতা চেক করল → ব্যাখ্যাসহ সমাধান → Skill আপডেট
```

### 7.3 খাতা চেক (MCQ বনাম Written)

| ধরন | চেক কীভাবে হবে? |
| --- | --- |
| MCQ | সরাসরি মিলিয়ে দেখা — সঠিক / ভুল, সঙ্গে সঙ্গে নম্বর |
| Written (Textarea) | LLM Rubric দিয়ে চেক করবে — মূল পয়েন্ট আছে কিনা, ভুল কোথায়, ব্যাখ্যাসহ সমাধান দেবে। ১০০% নিখুঁত হবে না — এটা আগেই PRD-তে বলা আছে। Student ভুল উত্তরের রিপোর্ট করতে পারবে, Admin ঠিক করবে। |

### 7.4 Skill আপডেটের নিয়ম

- সঠিক উত্তরে Skill বাড়বে, ভুলে কমবে।
- কঠিন প্রশ্নের সঠিক উত্তরে বেশি বাড়বে; সহজ প্রশ্নের ভুলে বেশি কমবে।
- একই টপিকে বারবার ভুল করলে ওই টপিকের Skill কমবে, আর AI ওই টপিক আবার পড়তে বলবে।
- সঠিক সংখ্যা / সূত্র (যেমন: কত নম্বরে লেভেল বদলাবে) `03-database-schema.md` ও `04-api-specification.md`-এ ঠিক করা হবে — এখানে শুধু নীতিটা ঠিক থাকল।

## 8. Auth, Roles ও Security

### 8.1 রোল

| রোল | যা করতে পারবে | যা করতে পারবে না |
| --- | --- | --- |
| **Student** | Register / Login, Dashboard, Category → Subject, শেখা, পরীক্ষা, নিজের প্রোফাইল / Progress দেখা | প্রশ্ন আপলোড / স্ক্র্যাপ, Admin Dashboard, অন্য Student-এর তথ্য |
| **Admin** | Scrape, Manual Upload, KB পরিচালনা, প্রশ্ন এডিট / ডিলিট, Review Queue, Student রিপোর্ট দেখা | Student-এর হয়ে পরীক্ষা দেওয়া (Admin-এর কাজ KB ঠিক রাখা, খাতা চেক করা নয় — সেটা AI করবে) |

### 8.2 নিরাপত্তার নিয়ম

- প্রতিটি API রিকোয়েস্টে JWT যাচাই হবে; রোল অনুযায়ী অনুমতি চেক হবে (RBAC)।
- Admin API-তে Student ঢুকতে পারবে না; Student API-তে একজন অন্যজনের তথ্য দেখতে পারবে না।
- পাসওয়ার্ড কখনো plain text-এ রাখা হবে না — শুধু hash থাকবে।
- আপলোড করা ফাইলের ধরন ও সাইজের সীমা থাকবে; অচেনা ফাইল চালানো হবে না।
- Student-এর ব্যক্তিগত তথ্য অন্য কাউকে দেওয়া হবে না।

### 8.3 খোলা সিদ্ধান্ত

- লগইন কী দিয়ে হবে — Email, Phone, নাকি Google? PRD 4.1-এ এখনো চূড়ান্ত হয়নি। Auth ডিজাইন এমন হবে যাতে যেকোনো একটা বসানো যায়, পরে অন্যটা যোগ করা যায়।

## 10. Non-Functional — গতি, খরচ, নির্ভরযোগ্যতা

| বিষয় | সিদ্ধান্ত |
| --- | --- |
| **গতি** | Student-এর পেজ খুলতে KB থেকে ডেটা সরাসরি আসবে; LLM-কে জিজ্ঞেস করে বানানো জিনিস (ব্যাখ্যা, প্রশ্ন) একবার বানিয়ে জমিয়ে রাখা হবে, প্রতিবার নতুন করে বানানো হবে না |
| **LLM খরচ** | সবচেয়ে বড় খরচের জায়গা। নিয়ম: (1) একই টপিকের ব্যাখ্যা একবার বানিয়ে KB-তে রাখা; (2) পরীক্ষার প্রশ্ন বানানোর সময় অপ্রয়োজনীয় লম্বা উত্তর চাওয়া হবে না; (3) Admin প্রসেসিং ব্যাচে চালানো হবে |
| **নির্ভরযোগ্যতা** | Scrape / Upload ব্যাকগ্রাউন্ড Job-এ চলবে — একটা Job ব্যর্থ হলে Student-এর পড়া আটকাবে না; Job-এর অবস্থা (চলছে / শেষ / ব্যর্থ) Admin দেখতে পাবে |
| **ডেটা নিরাপত্তা** | নিয়মিত ব্যাকআপ; KB-র প্রতিটি পরিবর্তনের রেকর্ড (কে, কখন, কী বদলালো) রাখা হবে, যাতে ভুল প্রশ্ন ঢুকলে ফেরত যাওয়া যায় |
| **বাংলা** | ডেটাবেস utf8mb4; বাংলা টেক্সট, সংখ্যা ও ফন্ট সব জায়গায় ঠিকমতো দেখাতে হবে |
| **স্কেল** | MVP-তে একটাই ক্যাটাগরি, তাই ছোট সার্ভারেই চলবে। ক্যাটাগরি বাড়লে KB ও প্রশ্নের সংখ্যা বাড়বে — তখন Vector Search ও ক্যাশিং যোগ করার জায়গা এই আর্কিটেকচারে খোলা থাকবে |
